# 罠と教訓

**このプロジェクトで実際に踏んだものだけを書く。** 抽象的に正しいだけの話は書かない。

新しく踏んだら **1行足す**。各項目には次の2つを書く:

- **⚠️ 何が起きたか**（具体的な数字を入れる）
- **⭐ なぜ気づけなかったか** ← **こちらのほうが価値がある**

⭐ **既存の項目を形の上では守っていたのに壊れたときは、その項目を上書き・拡張する。**
（例：「対で入れる」→「入れたものが**実際に走るか**確かめる」）

⚠️ ここは**このプロジェクトの記録**。過去作 box の教訓は `参考/ゲーム開発から学んだこと.md`
にあり、そちらは**サンプル1件**なので、ジャンル固有の設計判断は転用しない。

## ⚠️ 自分で撮った画面は「知っている画面」として読んでしまう（2026-08-19）

**⚠️ 何が起きたか**: 全17画面を撮り、数値検査（重なり・はみ出し・明暗比）を
全部 0 件にしてから「整った」と報告した。そのあと**別のレビュアーに見た目だけを見てもらったら、
15件の指摘**が出た。しかも上位はどれも「壊れている」ではなく
**「未完成に見える」「主役が読めない」**という、数値では出ない種類だった。

代表例:

- 孵化器の枠が 300×400 の**白い空箱**で画面の半分を占め、未完成に見える
- **シアンが地の色**になっていて、アクセントが機能していない（絞る・並べるは一面真っ青）
- **選択の表現が3種類**（枠線／塗り／タブの塗り）。しかも「選択」と「使用中」が同じ橙のべた塗り
- 同じ「個体を選ぶ升」が**4通り**、卵の升が**3通り**あった

**⭐ なぜ気づけなかったか**: 検査が見るのは「重なっていないか」「はみ出していないか」で、
**「これは何をする画面か」「どこを押せばいいか」は測れない**。
そして自分は各画面の意図を知っているので、**空箱を見ても「卵が入る場所」と読めてしまう**。
知らない人には「白い箱」にしか見えない。

**対策**: ⭐ **全画面を撮ったら、外の目に見せる。**
⚠️ 「崩れ 0 件」は**必要条件であって十分条件ではない**。
⚠️ 撮るときは**覆いを開いた状態も含めて全部**（今回17枚。うち9枚が覆い）。
⚠️ 一覧が空だと問題が見えないので、**中身を入れてから撮る**
（保存は退避してから増やし、撮り終えたら戻す）。

⭐ ただし**採らない指摘もある** ── 今回は「技の並びを揃えろ」を作者判断で不採用にした。
レビューは意図を知らないので、**意図してそうしているものまで「不揃い」と読む**。

## ⚠️ 「直した」と言った色が、Prefab には届いていなかった（2026-08-19）

**⚠️ 何が起きたか**: 2026-08-18 に「うすい文字を濃くした（3.0/1.9 → 7.6/5.4）」と
記録したが、⭐ **直したのはコードの定数だけ**だった。
Prefab に**焼き付いていた古い灰（142,147,168・比 3.0）が 12個**そのまま残り、
巣の札の「Lv」などは うすいままだった。

**⭐ なぜ気づけなかったか**: 定数を直せば全部変わる、と思い込んでいた。
⚠️ この作りは「並び・色は Prefab が持つ」が原則なので、**定数はむしろ例外**。
実行時に上書きする欄（`CreaturePanel.Bind` など）は直り、
書き出したきり触らない欄は直らない ── **同じ色が2つの経路を持っていた**。

**対策**: ⭐ **色を変えたら Prefab をさらう。**
`GetComponentsInChildren<Text>` で明暗比を測り、目安未満を機械的に拾って置き換える。

**⚠️ 測り方の罠**: 「白い札の上」と決め打ちで比を出すと嘘が出る
（濃紺のピルに載った**白い字が 1.0**＝最悪と報告された）。
⭐ 実際に後ろにある面（alpha が十分な最初の祖先の Image）を辿ってから比べる。

**⚠️ もう1つ**: 面と字で**同じ色を使い回していた**。器が鋼色から白へ変わった日に、
面の明るさだけが正しく、字が取り残された（緑 3.1 / 赤 3.9 / 橙 2.1）。
⭐ `Accent` / `Good` / `Danger` は**面専用**、字は `AccentInk` / `GoodInk` / `DangerInk` と分けた。

## ⚠️ 同じ寸法を2か所に書いて、半年ぶんずれていた（2026-08-19）

**⚠️ 何が起きたか**: 升の型（`CreatureCell.prefab`）は **328×300**、
一覧の格子は **228×200** を配っていた。中身は 328 の前提で置いてあるので、

- 絵が中心から **50 右**へずれる
- 選んだ印（328 幅）が**隣の升へ 100 はみ出す**
- 特性の丸（x 284）が升の外へ落ちる

**⭐ なぜ気づけなかったか**: **どちらも「正しい数」に見える。**
型を大きくした人は型の中で辻褄を合わせ、格子の数は誰も触らなかった。
⚠️ 画面は「絵が少し右寄り」にしか見えず、**壊れているように見えない**。
検査道具も、升の中身が升の外へ出ることは見ていなかった。

**対策**: ⭐ **寸法の出所を1つにする。**格子は型の `sizeDelta` を読む。
⚠️ 「両方に同じ数を書いて、変えるときは両方直す」は必ず破られる。

**続き（同じ日）**: 出所を1つにしたら、今度は**測る時点**が問題になった。
⚠️ 敷き直した瞬間はまだレイアウトが走っておらず、配合の器は そのあと
1080 → 984 に縮む。1080 の前提で 3列（1008 幅）を並べ、右端が切れた。
⭐ 幅を見張って、変わったら測り直す（`LayoutRebuilder.ForceRebuildLayoutImmediate` も通す）。

## ⚠️ 検査道具が「異常なし」と嘘をついた（2026-08-18）

**同じ日に2つ出た。どちらも「0件」と報告する形で壊れていた。**
⭐ 道具の壊れ方として最悪 ── 何も無いことを「異常なし」と読み違える。

### ① 別の覆いを掴んでいた

`InspectScreens.Report()` が `Object.FindAnyObjectByType<Canvas>()` で覆いを探していた。
⚠️ 戦闘中は演出用の **`Fx` も Canvas** なので、そちらを掴むと
**「調べた部品: 0　重なり 0件」**と出る。実際にそれを見て「直った」と判断しかけた。

**直し**: 子を一番多く抱えている Canvas を本体とみなす（`Screenful()`）。
⚠️ `FindAnyObjectByType` は**どれが返るか決まっていない**。同じ型が2つ以上ある
場面では使わない。

### ② 覆いの中と外を比べていた

札（合成・ステ・技の詳細）は、後ろを押させないために画面いっぱいの Button を敷く。
⚠️ その札を1枚開くだけで「画面中の部品と重なった」と出る（実測: ステ 9件、技 4件）。
⚠️ 嘘の警告を出す道具は、そのうち誰にも読まれなくなる。

**直し**: どの覆いの上に載っているかで**層**を出し、層が違うものは比べない（`LayerOf()`）。
⭐ 覆いの中の札どうしは今までどおり比べる。

### ③ 切り取られて見えていないものを数えていた（2026-08-19 追加）

巻物（ScrollRect + RectMask2D）の中身は、器の外へ出たぶんが**描かれない**。
⚠️ それを数えていたので、一覧を下までスクロールしていないだけで
「升が『決定』の押しどころと重なっている」と出た（実測 3件）。

**直し**: 祖先の `RectMask2D` で四角を切り、まったく見えないものは数えない（`Clip()`）。

### 教訓

⚠️ **「0件」を見たら、まず「本当に見に行ったのか」を疑う。**
部品の数も一緒に出しておくと気づける（0個で0件は異常なし ではない）。

⚠️ **逆に「N件」も疑う。**この道具は3回とも
「**画面には出ていないもの**を数えていた」形で嘘をついた
（別の覆い／覆いの外／切り取られた先）。
⭐ 重なりを数える前に「**それは本当に描かれているか**」を先に決めること。


## 1. `import`/`export` の無い .ts はモジュールにならない

⚠️ **何が起きたか**: `src/main.ts` と `src/gallery/main.ts` に同名の `render` / `root` を
書いたら、別ファイルなのに `TS2393 Duplicate function implementation` で落ちた。

⭐ **なぜ気づけなかったか**: 「別ファイル＝別スコープ」だと思い込んでいた。
TypeScript は**トップレベルに import/export が1つも無いファイルをスクリプト扱い**にし、
宣言がグローバルへ漏れる。エントリポイントは副作用だけで export する物が無いので、この形になりやすい。

**対策**: エントリポイントの末尾に `export {}` を置く。

## 2. 禁止語を探す検査は、禁止語の**説明文**を検出する

⚠️ **何が起きたか**: `check-determinism.mjs` を初めて走らせたら、
`src/core/rng.ts:3` の「`Math.random()` は使わない」という**注意書きそのもの**を
違反として報告した。1件目の実行がいきなり赤になった。

⭐ **なぜ気づけなかったか**: 「禁止語を grep する」という発想は正しい。
見落としたのは、**禁止するものほど、それを説明する文章がコードベース中に増える**こと。
禁止が徹底されるほど、コメント側の出現数だけが増えていく。

**対策**: コメント（`//` と `/* */`）を剥がしてから照合する。
⭐ 併せて**空振り検査**をした — 本物の違反2件を仕込んで捕まること、
`// determinism-ok:` を付けた行は通ることを確認。
これをやらないと「緑だが何も守っていない検査」になる。

## 3. 不変条件を強く書きすぎると、正しい実装が落ちる

⚠️ **何が起きたか**: ステ合計上限の削りを検査するのに
「削る前に a ≧ b なら、削った後も a ≧ b」という不変条件を書いたら、
10万件中 **20,530件が違反**と出た。実装を疑って読み直したが、実装は正しかった。

原因は **整数の端数**。`[5,5,5,5]` から3だけ削るとき、4つとも同値なので
誰か1つが端数を被る → `[4,4,4,5]`。「同値だったのに開いた」ので、
非厳密な不等号で書いた不変条件に引っかかる。

⭐ **なぜ気づけなかったか**: 「特化が保たれる」という**日本語の意図は正しかった**。
それを式に落とすときに、**同値の扱いを考えていなかった**。
検査が赤いとまず実装を疑うが、この形では**測る側が間違っている**。

**対策**: 不変条件は「厳密に大きかったものは逆転しない」＋
「同値だったものの開きは1以内」の2本に分けた。両方0件で通った。
⭐ 教訓の一般形: **正しく直しても、測るものが違えば失敗に見える。**
検査が落ちたら、実装と**検査の式の両方**を疑う。

## 4. 「変化が無い」と「死んでいる」を区別できない生存確認

⚠️ **何が起きたか**: `npm run same` が、**開いているタブ**を
「286秒 申告が無い — このタブは閉じている可能性がある」と報告した。

原因は `src/live/report.ts` に入れた最適化 —
「**中身が変わったときだけ送る**」（ファイルの更新時刻を無駄に動かさないため）。
保管庫の画面は内容が変わらないので、初回以降**一度も申告しなかった**。

⭐ **なぜ気づけなかったか**: 最適化そのものは正しい判断に見えた。
見落としたのは、**同じ1本の申告に「内容」と「生存」の2つの意味を載せていた**こと。
内容が変わらないことを理由に送信を止めると、**生存の情報も一緒に止まる。**
（前作の「1つの旗に2つの意味を持たせる」と同じ形）

⚠️ **危なかったのは診断のほう**: 最初「ブラウザが背面タブのタイマーを絞っている」と
**推測しかけた**。10秒おきに80秒サンプリングしたら、申告が
30→41→51→…→111秒 と**一度も戻っていない**＝絞られているのではなく**完全に止まっている**、
と分かって自分の実装に行き着いた。
⭐ **対照を取らない診断は診断ではない。**

**対策**: 中身が変わらなくても毎回送る。
書き込み回数を惜しむより**生存確認のほうが価値がある**（`.live.json` は git 管理外）。
修正後に測り直し: 80秒間ずっと最終申告から1〜3秒。

## 5. `npm run dev` を止めても vite の子プロセスが残る（Windows）

⚠️ **何が起きたか**: 開発サーバーを止めたつもりで `netstat` を見たら、
**PID 26140 がまだ 5815 を LISTENING で握っていた**。
止まったのは `npm` の親プロセスだけで、その下の vite は孤児として生き残っていた。

⭐ **なぜ気づけなかったか**: 「止めるコマンドがエラーなく返った」ことを
「止まった」と読んでいた。**止めたい対象は npm ではなくポートを握っている当人**。

**対策**: `npm run stop`（`scripts/stop.mjs`）を作った。
ポートを LISTENING で握っている PID を `netstat -ano` で探し、
`taskkill /T /F` で子ごと落とす。冪等（既に解放済みなら何もしない）。
⚠️ **止めたら必ずポートを見る。**「コマンドが返った」は根拠にならない。

## 6. Git Bash から `cmd` 経由で日本語ファイル名の .bat を呼ぶと見つからない

⚠️ **何が起きたか**: `cmd //c "ゲームを開く.bat"` が
「内部コマンドまたは外部コマンド…として認識されていません」で落ちた。
ファイルは確かに存在する。

⭐ **なぜ気づけなかったか**: 「日本語を .bat の**中身**に書くと壊れる」は知っていたが、
**ファイル名の受け渡し**でも同じことが起きるとは結び付いていなかった。
Git Bash が UTF-8 で渡した名前を、cmd.exe が cp932 で読むためズレる。

**対策**: 日本語名のファイルを叩くときは **PowerShell を使う**
（`& ".\ゲームを開く.bat"` は通った）。
⚠️ なお**ユーザーがエクスプローラーからダブルクリックする経路では起きない**。
壊れているのは shell を跨ぐときだけなので、bat 自体を ASCII 名に変える必要はない。

## 7. `.gitattributes` は後の行が勝つ — 個別指定を先に書くと黙って死ぬ

⚠️ **何が起きたか**: `.bat` を CRLF に保つつもりで書いたのに、
`git check-attr` に訊いたら **`eol: lf`** が適用されていた。

```
*.bat text eol=crlf      ← 先に書いた個別指定
* text=auto eol=lf       ← 後に書いた一般規則が勝ってしまう
```

このまま clone すると **LF の .bat** ができ、cmd.exe が黙って失敗する（罠の連鎖）。

⭐ **なぜ気づけなかったか**: CSS の後勝ちは意識するのに、`.gitattributes` も
同じ規則だと結び付いていなかった。しかも**症状が出るのは clone した後**なので、
書いた本人の手元では最後まで気づけない。

**対策**: 一般規則を先、個別の上書きを後。
⭐ そして**記述を読んで判断せず `git check-attr -a <file>` でツールに訊く。**
今回もコミット時の警告は正しい設定でも間違った設定でも同じ文言だったので、
警告だけでは見分けられなかった。

## 8. 「比だけ」で決まる式は、特化を構造的に無意味にする

⚠️ **何が起きたか**: ダメージを `power × 2a / (a + d)` にしていた。
爆発を避ける狙いは正しかったが、この式は **a と d の比だけ**で決まる。
攻撃特化(a=60) が防御特化(d=60) を殴っても比は 1 で、
**均等どうし(a=40,d=40)と同じダメージ**にしかならない。

結果、企画が保証したかった「得意を2つ作れる」が成立せず、実測で
**均等の総合勝率 82% に対して「得意2つ」の攻速が 22%** という逆転が起きた。
合計上限を1ステ上限の2倍にした意味が丸ごと消えていた。

⭐ **なぜ気づけなかったか**: 式を選ぶとき「爆発しないか」だけを見て、
**「特化が報われるか」を見ていなかった**。企画の中心にある性質なのに、
式がそれを殺しうるとは考えていなかった。

**対策**: 分子・分母とも定数で底上げする `power × (A+a) / (D+d)` に変えた。
**絶対値が効く**ので特化が報われ、定数があるので爆発もしない。

## 9. 対照の取り方を2回続けて間違えた

⚠️ **何が起きたか**: 釣り合いを測るのに
①**全員が手当を持つパーティ**で戦闘の長さを測り（回復役3体どうしの持久戦になり、
1体落とすのに62行動）、
②**同じ特化型を3体並べた編成 vs 均等3体**で特化の是非を測った。

②が特に悪い。企画が謳うのは「**得意2つ × 3体 = 6枠でパーティを組む**」＝
**役割の違う特化を組み合わせる**ことで、壁役ゼロの攻速3体編成は誰も組まない。
測っていたのは企画が主張していない構成だった。

⭐ **なぜ気づけなかったか**: 「変数を1つだけ変える」という実験の作法に忠実だったから。
型を比べるなら他を揃えるのが正しい。**だが揃えた結果が、誰も通らない条件になっていた。**
既定値は「代表的な状態」ではない、の別の顔。

**対策**: 釣り合いの検査には**編成どうしの比較**（`--party`）を別に用意した。
⚠️ 「変数を揃える検査」と「実際に通る条件の検査」は**別物で、両方要る**。

## 10. 集中攻撃は防御の価値を攻撃の約3倍にする / 「壁」は仕組みが無いと存在しない

⚠️ **何が起きたか**: 役割を分けた編成（壁・火力・補助）の勝率が **23%** しかなかった。
敵は最も脆い相手から狙うので、脆い火力役が真っ先に落ちて 2v3 になる。

⭐ **2つのことが同時に見えた**:
1. **3v3 の集中攻撃では、狙われた1体は毎ラウンド3発受ける。**
   だから防御は3回効き、攻撃は自分の1発にしか効かない。**防御の価値が約3倍**になる
2. **企画は「壁」を役割として挙げていたのに、壁を成立させる仕組みが無かった。**
   耐久型は「自分が死なない」だけで、味方を守れない

**対策**: 「かばう」（味方への単体攻撃を肩代わり）を足した。
これは機能追加ではなく**企画に書いてあった役割の実装**。
実測: 役割分担編成 23.3% → **50.7%**。肩代わりを持たない同じ編成は 20.1% なので、
**この仕組みだけで 30 ポイント**動いている。

⭐ 教訓: **役割の名前を企画に書いただけでは、その役割は存在しない。**
成立させる仕組みがあるかを、実測で確かめる。

## 11. `justify-items: start` は `width: 100%` を内容幅にしてしまう

⚠️ **何が起きたか**: 戦闘画面で HP バーの長さが個体ごとにバラバラだった。
`.fighter` を `display: grid; justify-items: start` にしていたため、
中の `.meter { width: 100% }` の 100% が**グリッド列の幅ではなく内容幅**に解決されていた。

⭐ **なぜ気づけなかったか**: 用意していた数値検査は
「はみ出し」「重なり」「見切れ」「横スクロール」を見るもので、
**どれにも当たらない**。バーは親に収まっているし、重なってもいないし、切れてもいない。
**ただ長さが揃っていないだけ**なので、全部素通りした。
気づいたのは切り出し画像を目で見たとき。

**対策**: `justify-items: stretch` にして、絵だけ `justify-self: start`。
⭐ そして検査に「**揃っているはずの寸法が揃っているか**」を足した
（同じ役割の要素の幅を集めて `new Set(...).size === 1` を見る）。
⚠️ **「壊れていないか」の検査は「揃っているか」を見ない。** 両方要る。

## 12. 暗い意匠は暗い背景に沈み、意匠の不具合に見える

⚠️ **何が起きたか**: ギャラリーでハネルが「離れた四角が2つ」に見えた。
意匠の格子を疑って書き直したが直らない。画素を読んだら **row 7 は16画素とも
不透明で繋がっていた** — 消えていたのは輪郭色 `#241c2e` で、
市松の背景 `#262320` とほぼ同じだった。

⭐ **なぜ気づけなかったか**: 「絵が変に見える → 絵が悪い」と読んだ。
**地の色を疑う発想が無かった。**
しかも市松は「透明を示すための背景」なので、正しく機能しているつもりでいた。

**対策**: 市松を**中間の明度**にした（`#5a5650` / `#4c4842`）。
暗い意匠も明るい意匠も、どちらも地から浮く。
⭐ そして **見た目がおかしいときは、まず画素を読む。**
今回も「意匠を直す」方向へ2手費やしてから、読んで気づいた。

## 13. 数値検査は「壊れている」を見るが「意図した並びか」は見ない

⚠️ **何が起きたか**: 巣の一覧が
「浅瀬の巣タマル · 鱗 · 段階1素質 ~24/80」と**全部繋がって**表示された。
`.ident` に縦並びの指定を入れ忘れ、3つの `<span>` が横に流れていた。

⭐ **なぜ気づけなかったか**: 用意していた数値検査は全部通った。
はみ出していない・重なっていない・見切れていない・横スクロールもしていない。
**ただ意図した並びになっていないだけ**なので、どの検査にも当たらない。
気づいたのは切り出し画像を目で見たとき。

⚠️ これで**同じ形が2回目**（§11 は「揃っているはずの寸法が揃っていない」だった）。
どちらも「壊れていないが、意図と違う」。

**対策**: 見た目を触ったら**必ず切り出して目で見る**。
数値検査は目視の代わりにならない。
⭐ 教訓の一般形: **検査は「自分が想像した壊れ方」しか見つけられない。**
想像していない壊れ方は、目でしか見つからない。

## 14. 自動で対象を選ぶと、HP の高い相手は永久に狙われない

⚠️ **何が起きたか**: ボス戦で **ボス本体に与えた総ダメージが 0** のまま負け続けた。
ボスを弱くしても数字が1つも変わらず、最初は「弱くした処理が効いていない」と疑った。

原因は単純だった。単体攻撃の対象を「**残 HP の低い相手**」に自動で決めていたので、
HP が最も高いボスは**眷属が全滅するまで一度も狙われない**。そして眷属を倒し切る前に
味方が全滅していた。

⭐ **なぜ気づけなかったか**: 「残 HP の低い相手から倒す」は集中攻撃として正しい。
正しい方針が、**HP の高い個体を実質無敵にする**とは思っていなかった。
しかも「触れない」と「硬い」は**症状が同じ（勝てない）**なので、数値を見るまで区別できない。

**対策**: **プレイヤーが対象を選べるようにした**。指定が無いとき（AI）だけ従来の自動に落ちる。
⚠️ 併せて、**敵の総 HP がパーティの出せる総ダメージを超えないところ**にボスを置いた。
超えていると、プレイヤーは「ボスに一度も触れないまま負ける」という一番つまらない負け方をする。

## 15. 検証コードの前提が間違っていて、2回測り損ねた

⚠️ **何が起きたか**: ボス調整で2回、**測る側のミス**で結論を誤った。

1. 「素質120のパーティ」を作るのに、`applyTotalCap(wild)` で**先に80へ削ってから**
   変異カウンタを20に書き換えていた。削られた値は戻らないので、実際は素質80のままだった。
   （素質80と120で結果が同一だったのが手がかり）
2. 「鱗のボスには牙が有利」と読んで検証編成を組んだが、3すくみは 牙 → 羽 → **鱗** → 牙。
   鱗に有利を取るのは**羽**だった。**自分で書いた表を読み違えていた。**

⭐ **なぜ気づけなかったか**: どちらも「実装が悪い」という前提で読んでいた。
⚠️ **同じ数字が2回出たら、まず測り方を疑う。** 実装を変えたのに結果が1ビットも動かないのは、
実装が効いていないか、**測っていないか**のどちらか。

**対策**: 上限を掛ける関数は**変異カウンタを引数で受け取る**（後から書き換えられない形）。
有利不利のような対称でない関係は、**表を読むのではなく関数に訊く**。

## 16. 「常に使える枠」を作ると、そこに置いた大技が壊れる

⚠️ **何が起きたか**: 「たたかう」を廃止し、**枠1（種族固定）の CT を 0** にした。
枠1が常に打てるので手が無くならない、という狙いは正しかった。

⚠️ だが**ヌシの枠1は震撼（CT7 の全体・大技）**だった。
CT が消えた結果、ボスが**毎回 震撼を撃つ**ようになり、決着が **8行動**になった
（他の種族は 30〜50行動）。**「CT が長いぶん重い」という技の設計が丸ごと無効化された。**

⭐ **なぜ気づけなかったか**: 「枠1は CT なし」という規則と
「震撼は CT7 の大技」という設計を、**別々の場所で別々の日に決めていた**。
どちらも単体では正しく、噛み合わせたときだけ壊れる。

**対策**: 震撼を枠2へ移し、**枠1の威力は「小〜中」までという規則**を足した。
⭐ そして `auditSpecies()` に**機械の検査**を入れた
（枠1の技が 大/特大 なら起動時に落ちる）。
⚠️ **規則を文章で書くだけでは、次に種族を足す日に同じことをやる。**

## 17. 状態を進めないボタンを押して「動いていない」と誤診した

⚠️ **何が起きたか**: ゲージのリアルタイム更新を確かめようとして、
技のボタンを押してからゲージを測ったが、**12回サンプリングして1ミリも動かなかった**。
「描画ループが回っていない」と疑った。

原因は**対象選択**。単体攻撃は技を押しただけでは実行されず、
**敵を選ぶまで待つ**ようになっていた（自分でその日に足した機能）。
状態が進んでいないのだから、ゲージが動かないのは当たり前だった。

⭐ **なぜ気づけなかったか**: 検証の手順が**自分の実装より古かった**。
「ボタンを押せば行動する」は、対象選択を足す前の常識。

**対策**: 動きを測る前に、**まず状態が変わったことを確かめる**
（ログが伸びたか、HP が減ったか）。変わっていないなら、測る対象ではなく**操作**を疑う。

## 18. アニメーションをフレーム数で進めていて、遅い環境で終わらなかった

⚠️ **何が起きたか**: 発射の軌跡を「1フレームあたり 3 刻み」で進めていた。
自分の環境では 1秒で終わるのに、検証用のブラウザでは **rAF が 2fps** しか出ておらず、
200 刻みの軌跡に **33秒**かかって終わらない。「発射が動いていない」と誤診した。

⭐ **なぜ気づけなかったか**: 自分の機械で見たときは正しく動いていた。
フレーム数で進めると**表示速度が機械の速さで変わる**ので、
60Hz と 144Hz で 2.4倍違う画面になる。これは「遅い環境の問題」ではなく**実装の誤り**。

**対策**: `requestAnimationFrame(now)` の時刻を使い、**経過時間**で進める。
所要時間は距離なりに伸ばしつつ上下を抑える（0.7〜2.0秒）。

## 19. 「狙いを寛容にする」調整で、避けるべき相手が塗り絵になった

⚠️ **何が起きたか**: 発射フェーズの角度の幅が狭すぎたので、隙間を 74 → 90 に広げた。
走査では「段ごとに要るスピードは変わらず、境目の鋭さだけ減った」と出たので採用した。
ところが実物で撃ってみると、**まっすぐ上に飛ばすだけで卵に届いた**。
広げた隙間が開始位置を飲み込み、**親が避けるべき障害ではなくなっていた**。

⭐ **なぜ気づけなかったか**: 測っていたのが「成功する角度の幅」と「必要な距離」だけで、
**「まっすぐで通るか」を測っていなかった**。幅はむしろ広がって良く見えていたので、
数値だけ見ていると「改善した」としか読めない。
⚠️ 壊したのは**その調整で守られるはずだった性質そのもの**（「親が立ちはだかる」）。

**対策**: 調整の根拠にした性質を**そのまま検査に足す**。
`--steal` に「どの巣もまっすぐでは通らないか」を入れ、実際に落ちることを確かめた
（隙間 90 / 寄り 34 で「通る,通る」と出る）。
⭐ 幅・距離のような**間接的な指標だけを見ない**。守りたい性質を直接叩く。

## 20. 資料から読み取ったのに、読み取った半分しか実装しなかった

⚠️ **何が起きたか**: ユーザーが作った画面モックを受け取り、配色・輪郭・影・書体を取り出して
適用した。**構成（三角配置 / 左に味方3体 / 下部4パネル）も読み取って報告していた**のに、
実装は既存の画面構成のままで、色だけ差し替えて「反映しました」と報告した。
ユーザーから「画面構成が送ったものと全然違う」と指摘された。

⭐ **なぜ気づけなかったか**: 「UI はモック」という合意を、自分の中で**無意識に「配色はモック」に
狭めていた**。狭めた事実を言葉にしていないので、自分でも検算できない。
⚠️ しかも**読み取れていた**（報告文に構成が書いてある）。分かっていて適用しなかったのが悪い。

**対策**: 資料を採るときは「**何を採って何を採らないか**」を先に列挙して、
採らないものには理由を書く。暗黙に狭めない。
⭐ 特に「読み取った内容を報告した」ときは、**その報告文が実装のチェックリストになる**。
報告に書いて実装していない項目が残っていないか、最後に自分の報告文と突き合わせる。

区別していなかった。7つ並んでいる時点で「これは一覧表であって、1画面の姿ではない」と
読めたはずだった。

**対策**: 見本が**複数まとめて置かれている**ときは、まとめるための枠・番号・ラベル・影は

## 22. 「はみ出し検査」が縦しか見ておらず、横スクロールを見逃した

⚠️ **何が起きたか**: 画面の要素が器の外に出ていないかを `getBoundingClientRect` で
検査して「見切れ 0」と報告した。ところが 320px の端末で戦闘画面を見ると、
**場が横にスクロール**していた。列幅を `158px` 固定にしていたためで、
158 + 10 + 148 = 316 が 292 の枠に入っていなかった。

⭐ **なぜ気づけなかったか**: 検査が「**器からはみ出した要素**」だけを見ていて、
**入れ子の中で横に溢れている**ことを見ていなかった。しかも縦スクロール層の中だったので
「スクロールすれば見える」として除外までしていた。⚠️ 縦は除外してよいが**横は駄目**。

**対策**: `el.scrollWidth > el.clientWidth` を**全要素**で見る。
ただし `overflow-x: visible` の要素は「見えている」ので除く（雲やバッジの意図的なはみ出し）。
⭐ 縦持ちの画面で横に動くものがあったら、それは全部事故。

## 23. 大きさを px で決め打ちして、狭い端末で必ず壊れた

⚠️ **何が起きたか**: 発射のフィールドを `350×540`、ホームのドット倍率を `10倍`、
戦闘の列幅を `158px`、器の幅を `390px` で決め打ちしていた。
320×568（iPhone SE）で見ると、フィールドがはみ出し、ホームの3体が重なり、
場が横スクロールした。

⭐ **なぜ気づけなかったか**: **自分が見ていた幅が1つだけ**だった（460×880）。
実機は 320〜430 まで幅が、568〜932 まで高さが違う。
1つの寸法で合わせた値は、その寸法でしか合わない。

**対策**:
- 幅は `min(100%, 430px)`、文字は `clamp()`、位置は `%`
- **絵の大きさは `ResizeObserver` で実測してから決める**。ドット絵は**整数倍だけ**選ぶ
  （小数倍で拡大するとボケる）
- ⚠️ canvas は `width` 属性が描画面で、CSS の `border` はその外側に付く。
  **枠線ぶんを引かないと必ず溢れる**（4px×2 で 8px はみ出していた）
- 検査は **320×568 / 360×640 / 390×844 / 430×932 の4つで回す**。1つで通っても通ったことにならない

## 25. 共有ルールが後ろにあって、個別の `display` を打ち消していた

⚠️ **何が起きたか**: `.battle { display: grid; grid-template-rows: minmax(0,1fr) auto }` と書いたのに、
場が中身なりの高さ（302px）で止まり、シートの下に 226px の空白が残った。
原因は、**後ろにある共有ルール** `.nests, .hatch, .home, .steal, .battle, ... { display: flex }` が
`display: grid` を打ち消していたこと。詳細度が同じなので**後勝ち**。

⭐ **なぜ気づけなかったか**: 「自分のブロックのほうが後に書いてある」と**記憶で**思っていた。
見た目では「なんとなく余白が多い」だけで、原因が cascade だとは読めない。

**対策**: 自分でレイアウトを組む要素は、**共有の並べ方ルールに混ぜない**。
⭐ 疑ったら `getComputedStyle(el).display` と、その要素に当たっている CSS ルールを
**実際に列挙して**確かめる（`document.styleSheets` を舐めれば出る）。

## 26. grid の `space-between` が、空きが負のときトラックを重ねた

⚠️ **何が起きたか**: `grid-template-rows: auto auto` ＋ `align-content: space-between` で
場を組んだら、320×568 で**敵の HP バーが真ん中の味方に乗った**。
空きが負（中身の合計 > 器）になると `space-between` はトラックを重ねる。

⭐ **なぜ気づけなかったか**: 検査が「**枠からはみ出したか**」しか見ていなかった。
枠の中で要素どうしが乗り合っているのは、はみ出し検査に一切かからない。

**対策**:
- 器が縮む場所で `space-between` / `space-around` を使わない。**`1fr` で余りを吸わせる**（負の空きが生まれない）
- 検査に**重なり判定**を足した（`.fighter` や `.nestcard` などの塊どうしの矩形交差）。
  実際に足した直後、残っていた重なりを1件捕まえた

## 27. 「絵以外の高さ」を推測して倍率の表を書いた

⚠️ **何が起きたか**: 敵の絵の倍率を「場が440px以上なら12倍、340以上なら10倍…」という表で決めた。
320×568 で**行136px に中身173px** になり、味方に重なった。
絵以外（属性ピル・数値・HP・ゲージ・隙間）の高さを推測していたのが原因。

⭐ **なぜ気づけなかったか**: 表の見た目が「ちゃんと段階を踏んでいる」ので、根拠があるように見える。
実際は**一つも測っていない**数字だった。

**対策**: 絵以外の高さは**その場で測れる**。
`行の高さ − (塊の高さ − 絵の高さ)` で使える高さを出し、それを 16 で割って整数倍を取る。
⭐ 表を書きたくなったら、その数字が測れるものかどうかを先に考える。

## 28. 自分で書いた作法を読まずに作り、3つ同時に破った

⚠️ **何が起きたか**: `pixelizer` をスマホ向けに作ったとき、Wiki「スマホの作法」と
memory の `mobile-layout-rules` を**一度も開かずに**設計した。結果、決めてあった作法を
3つ破り、ユーザーから3つとも不満として返ってきた。

| 決めてあったこと | 作ったもの | 返ってきた言葉 |
|---|---|---|
| 器は **3層** | 4層（上バー・canvas・ドック・タブ） | 「機能が分散していて使いにくい」 |
| 高さは **`100svh`**（`100dvh` は下段が動く） | `100dvh` | 「バーがぐらぐらする」 |
| **二重スクロールを作らない。1画面に1つ** | 板3枚が内部スクロール | 「ツールを使うためにスクロール」 |

さらに、元の版に入っていた `scrollbar-gutter: stable` を書き直しで**落として**いた。
スクロールバーが出入りするたび中身が横にずれる（「横にも余白があって」）。

⭐ **なぜ気づけなかったか**: 「別プロジェクトだから」と作法を参照しなかった。
だが破ったのは**スマホという器の作法**で、中身が何かに依存しない。
しかも memory の索引には「スマホ前提のレイアウト作法」という行が見えていた。

**対策**:
- **スマホに載せるものを作るときは、着手前に `mobile-layout-rules` と
  Wiki「スマホの作法」を開く。** プロジェクトが違っても器の作法は共通。
- 作り終えたら、作法の表を1行ずつ**実測で照合**する（層の数 / 高さの単位 /
  スクロール層の数 / `scrollbar-gutter`）。目視では層の数すら数え間違える。
- 書き直しのときは、**元の版に入っていた指定を落としていないか**を差分で見る。
  `scrollbar-gutter` のような1行は、消えても画面が壊れないので気づけない。

## 29. 「種類」で分類して、頻度の違うものを同じ引き出しに入れた

⚠️ **何が起きたか**: `pixelizer` の設定を 画像 / 変換 / 色 / コマ / レイヤー / 出力 の
6タブに分けた。分類としては綺麗だが、**毎秒使う「色」が、1セッションに1回の
「変換」「出力」と同じ深さ**に沈んだ。色を選ぶのに2タップ＋スクロールが要る状態だった。

⭐ **なぜ気づけなかったか**: 分類が「意味」で見て正しかったから。
だが置き場所を決めるのは意味ではなく**使う頻度**。

**対策**: 道具を作るときは、まず**頻度で3段に割る**。

| 頻度 | 置き場所 |
|---|---|
| 毎秒〜毎分（対象・道具・現在の色） | **常時表示。タップ0** |
| 数分に1回（コマ・レイヤー） | 1タップ |
| 1セッションに1〜2回（読み込み・設定・書き出し） | 引き出しでよい |

⭐ 既存のエディター（Piskel / Aseprite / Pixelorama / dotpict）は例外なく
**canvas・道具・色を同時に見せて**いる。隠しているのは「まれ」だけ。
迷ったら、同じものを作っている実装が何を常時出しているかを見る。
参考: Aseprite の文書は「最も重要なのは sprite editor・timeline・color bar と
color picker・preview」と名指ししている。
