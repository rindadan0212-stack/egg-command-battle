# ゲーム開発から学んだこと

**ボクセル村シミュレーション「境木の村」(box) の開発記録から、次のプロジェクトへ持ち出せる形に
まとめたもの。** 2026-07 〜 2026-08、約1か月・約 130 のテストファイル・1,460 件の検査。

このファイルは**箇条書きの心得集ではない。**すべての項目が「実際に踏んで、時間を溶かした」
ものだけで構成されている。抽象的に正しいだけの話は書いていない。

---

## 0. この報告書の使い方

新しいゲームを始めるとき、**§9 のチェックリストだけ先に読む**。
それ以外は「何かがおかしいのに原因が分からない」ときに引く。

各項目には **⚠️ 何が起きたか** と **⭐ なぜ気づけなかったか** を付けてある。
後者のほうが価値がある — 同じ罠は形を変えて何度でも来るが、**気づけない理由は共通している**から。

---

## 1. 最も高くついた失敗の型

順番は「溶かした時間 × 再発回数」。この5つで、失った時間の大半を説明できる。

### 1.1 同じことを2箇所で決める

**最頻出。**別名で何度も来る。

| 形 | 実例 |
|---|---|
| 同じ**値**を2箇所 | 人口の必要数が2ファイルにあり、片方の編集が黙って消えた |
| 同じ**分類**を2箇所 | 「柵は防衛線か」を経路探索と戦闘が別々に判定し、柵だけ挙動が食い違った |
| 同じ**判断**を2箇所 | 「どれが頭か」を骨の名前と箱の位置で別々に判定 → 骨を足した日に頭が黒くなった |
| 見せた値と使う値 | ゴーストは描画ループの値、設置は再取得 → **見えていた場所と違う所に建つ** |
| 判定と実行 | 「行けるか」と「実際に歩く」が別関数 → 片方だけ直しても直らない |

⭐ **気づけない理由**: 2箇所目は「2箇所目に見えない」。定数の直書き・位置からの推測・
テストの中の期待値は、どれも「決めている」という自覚が無いまま第2の出所になる。

**対策**: 「これは誰が決めるか」を先に1つ決め、**その関数を作ったら grep して既存の直書きを
全部そこへ寄せるまでが1つの作業**。寄せ切らないと、寄せた事実が次の人を油断させるぶん悪化する。

### 1.2 片方向だけ変えて、対を放置する

**作る↔分解 / 符号化↔復号 / 積む↔壊す** のような対になった処理の、片方だけ比率を変える。

⚠️ 実例: 「資材4→建材1」を「資材1→建材4」に反転したとき、分解を旧比のまま放置。
**木材1 → 板4 → ほどいて木材16 の無限複製**ができた。

⭐ **気づけない理由**: そこには「往復しても増えも減りもしない」と**コメントが書いてあり、
テストもあった**。だが検査は片道しか測っておらず、**その等式が正方向を変えた瞬間に崩れる**
ことを誰も測っていなかった。

**対策**: **主張が「往復」なら往復を測る。** 片道の検査は往復を保証しない。

### 1.3 制約だけ足して、逃げ道を足さない（または足したものが動かない）

⚠️ 実例1: 「視線が通らないと攻撃できない」を守る側にも掛けたら、回り込む処理が無いぶん
膠着して**攻め側が得をした**。
⚠️ 実例2: 「高さが届かない敵は徘徊へ倒す」を入れたが、**その徘徊が一度も走っていなかった** —
経路の失敗フラグが敵ごとに1つしか無く、同じ tick の徘徊呼び出しを弾いていた。敵は攻撃も
徘徊もせず**その場で固まった**。

⭐ **気づけない理由**: 実例2 は「対で入れる」という教訓を**形の上では守っていた**。
足りなかったのは「**入れたものが実際に走るか確かめる**」こと。

**対策**: 「できなくする」と「代わりにこうする」は対で入れ、**代わりの側が実行される経路を
実測で確かめる**。共有状態（1本のパス・1つのフラグ）を2つの目的で使っている所は順序で干渉する。

### 1.4 尺度を変えると、意味が黙って変わる

⚠️ 1セル 0.5m → 1m に変えたら **1,204件中75件が落ちた**。原因はほぼ全部
「セル数の直書き」で、メートルで見ると倍の距離になった。

⭐ **より怖いのは落ちなかった側**:
- `for (let h = 1; h <= STEP_HEIGHT; h++)` が、尺度変更で上限 0.5 になり**一度も回らなくなった**
  → 自動で段差を登る処理が3日間まるごと死んでいた。型もテストも通る
- `PATH_MAX_NODES = 4000 * M * M` が黙って 1/4 になり、起伏を入れた日に村人が10日間立ち尽くした

**対策**:
- **距離・大きさは必ず `メートル値 * 単位` の形で書く**（この形の 334箇所は1つも壊れなかった）
- ⚠️ **上限・回数・添字に単位を掛けない**（セル数や試行回数は距離ではない）
- 尺度を変えたら「その値を別の尺度と比べている箇所」を全部 grep する

### 1.5 1つの旗に2つの意味を持たせる

⚠️ 実例: `passive`（襲わない）を「家畜の頭数」の判定にも使っていた。昼の湧きも中立にした
瞬間、**家畜が枠を奪われて一切湧かなくなり**、同時に世界の上限が効かなくなって
**上限60に対し96体**まで増えた。

⭐ **気づけない理由**: 1つ目の意味しか無かった時期は、その旗が正しく動いていた。
**2つ目の使い手が現れた日ではなく、3つ目が現れた日に壊れる。**

**対策**: 「振る舞い」と「出所」は別の欄にする。旗の名前が形容詞なら振る舞い、
名詞なら出所 — 混ざったら分ける合図。

## 2. 検証の作法

### 2.1 推測で原因を決めない。切り分けて測る

**この一行が、この開発で最も回収率が高かった。**

⚠️ 実例:
- 「草の描画が重い」と診断 → 実際は**影の描画コール**だった
- 「性能劣化は環境差」と報告された → 3回測ったら 2320/2330/2329ms と揃っていた（環境差ではない）
- 帯の検査が合わない → 仮説を**2回外し**、3度目に「外れている1点の内訳」を直接測って
  「そこは地形ではなく手で置いた目印だった」と判明

**対策**: 「Aが原因」と思ったら **A を無効化して比べる**。対照を取らない診断は診断ではない。

### 2.2 対照は「ユーザーが実際に通る条件」で取る

⚠️ 実例: 村人の救助の誤爆を直したが、素の条件では **1回 → 1回で差が出ず**、
「効いていない」と結論しかけた。ユーザーが実際に使う条件（勤務シフトを設定した状態）で
取り直したら **87回 → 0回**だった。

⭐ **気づけない理由**: 既定値は「代表的な状態」ではない。**機能の多くは、設定した人にしか効かない。**

### 2.3 否定を確かめる実験は、肯定側が起きることを先に見る

⚠️ 実例: 「エディタのページはもう再読込されない」を確かめようとしたが、
そもそも**そのファイルを取り込んでいない**だけで、何も証明していなかった。

**対策**: 「起きないこと」の確認は、**まず起きる条件で起きることを見てから**比べる。

### 2.4 空振り検査（実装を戻すと落ちるか）

テストを書いたら、**直した実装を一時的に戻して、そのテストが落ちることを確かめる。**

⚠️ この習慣で「通っているが何も守っていないテスト」を何度も捕まえた。
特に**意図が変わってテストを書き直したとき**は必須。緩めたのか直したのかは、これでしか分からない。

### 2.5 検査の数え方

- **「何件通ったか」ではなく「ファイル数が合っているか」を見る。**
  ⚠️ 実例: 19件のテストがワーカーごとメモリ不足で死に、**失敗ではなく集計から消えて**いた。
  緑に見えたので4日間気づかなかった。足し算が合わないときは、落ちているより悪い
- **既定より短い個別 timeout を書かない。** 単体で通りフルスイートでだけ落ちる = 偽の赤。
  この形の地雷が14箇所あった
- **同期の無限ループはテストのタイムアウトで止まらない。** ハングして集計から静かに抜ける

### 2.6 上限の式に大きな項があると、他の穴を吸収する

⚠️ 実例: 「地形の起伏は決めた帯に収まる」という検査が、**標本に手で置いた建造物を
混ぜていた**（5,261本中318本）。山の高さの項が大きかったので、34m の突出も帯に収まっていた。
**山を低くした日に初めて露見した。**

⭐ **教訓**: 大きな項は穴を隠す。**上限を下げた日に、それまでの検査の甘さが一気に出る。**

## 3. 見た目の作り方

### 3.1 数値検査と DOM は、見た目の破綻を検出できない

⚠️ 実例（全部、検査は全通過していた）:
- 受け渡し画面で**持ち物が折り返しの下に埋もれ**、白いボタンが壁のように並んでいた
- クラフト窓が地の面を持たず、**世界の草の上に文字が直に載って一行も読めなかった**
- 草花を入れたら**一本も見えなかった**（置いた緑が地面の緑とほぼ同色だった）
- 骨の木が**横に折り返して親子が読めなかった**（要素も文字も正しく存在していた）

**対策**: **UI・意匠を触ったら必ずスクショを見る。** ただし後述の罠に注意。

### 3.2 スクショの落とし穴

- **全体スクショは縮小されて届く。** 崩れ・被り・見切れは判定できない。
  → **要素単位で切り出して撮る**
- 親に `overflow:hidden` があると、**はみ出しは視覚的にクリップされ「整って見える」**
  → 親と子の矩形を**数値で比較**する
- **重なり・はみ出しは数値、配色・埋もれ・並び順は目**。役割が違うので両方要る

### 3.3 「本家と同じにして」は、記憶ではなく実物を当たる

⚠️ 実例: 一人称の持ち方を「たぶんこう」で書いて2回差し戻された。
実物は**モデル定義の3行**（`rotation [0,-90,25]`）で、引けば1度目から書けた。
「手が空のときだけ腕を描く」という条件も、1行調べれば分かった。

**対策**: 参考実装があるなら**定義ファイルを引く**。参考画像があるなら**そこから座標を読み取って
目標にする**。目分量の往復より速い（実測: 目分量で2回差し戻し → 測ってから3手で収束）。

### 3.4 測る指標そのものを疑う

⚠️ 実例: 夜を暗くしたとき「色が抜けたか」を彩度 `(max-min)/max` で測ったら、
**暗くするほど上がった**（0.722 → 0.831）。暗い画素では僅かな差でも1に近づくため。
「逆行した」と誤診しかけた。**緑の偏り `G-(R+B)/2`**（絶対量）に替えて解決。

⭐ **教訓**: **正しく直しても、測るものが違えば失敗に見える。**

### 3.5 最後は数字ではなく目で止める

⚠️ 実例: 夜の明るさに「昼の30〜35%」という目標を立てたが、**実測19%で止めた**。
30%まで戻すと遠景が読めてしまい「夜に出る理由」が消えるから。
**守るべきは輝度の比ではなく「自分の周りは読める / 遠くは分からなくてよい」という体験の線**だった。

**対策**: 数値目標は**作業の指針**であって合否ではない。目標のほうを実測に合わせて書き換えてよい。

### 3.6 その他、実際に効いた小さな知見

- **絵は「出す大きさ」から決める。** 32px で焼いて 44px と 26px の枠に出すと、整数でない
  拡縮で縁がガタつく。出す大きさより十分大きく焼いて縮小は平滑化に任せる
- **地面に置く飾りは、地面の色を引いてから色を決める**（同色だと消える）
- **ローポリで「たくさん生えている」は、細い葉を大量にではなく太い葉を数枚外へ倒す**
- **光る材質を物の全体に掛けない**（陰影が消えて「べた塗りの円錐」になる）
- **画面の向きは読み取りで決めない。目印を置いて撮る**（コードから推測した向きは2回とも外れ、
  4マス色を置いて撮ったら1発で分かった）

## 4. 設計の指針

### 4.1 将来を見越した抽象を作らない

⚠️ 実例: モーションの「時間の源」に `walk`（移動距離）と `clock`（実時間）の2種を用意したが、
**実装を見たら両方とも実時間**で、区別が何もしていなかった。区別ごと落とした。

**対策**: 「いつか要る」で枠を作らない。**要る日に足す。**
枠だけ作ると、以降ずっと「どちらで書くか」を考えるコストだけが残る。

### 4.2 全部を覆うつもりの表は、必ず数える検査を持つ

⚠️ 実例（同じ形が3回）:
- 職業を分類する表に後から足した2職が入っておらず、**その2職だけ永久にボーナスが付かなかった**
- 建物→職業の表に農夫が抜けており、**畑を建てても農夫にならなかった**
- ブロック名の表に形ブロックが無く、持ち物に「板の39」と出た

⭐ **共通点**: 型は通る。テストも通る。**ただ効かなくなるだけ**なので気づく手がかりが無い。
しかも3件目は「**使われた日**まで眠っていた」。

**対策**: 覆えているかを**数える検査**を書く（集合の差を取る）。

### 4.3 「〜まで待つ」に上限を置く

⚠️ 実例: 「敵が去るまで待つ」に上限が無く、**構造的に消えない敵**が1体居るだけで
進行が8日間止まった。条件を足して塞ぐ作業は終わらなかった。

**対策**: **保証したい不変条件は、条件ではなく上限で守る。** 待ちには必ず締切を置く。

### 4.4 「無ければ近道してよい」最適化は、前提が消えた日に壊れる

⚠️ 実例: 「壁が無ければ直線移動で足りる」は*地面が平らな世界*でだけ正しかった。
起伏を入れた瞬間、荷を持った敵が丘に突き当たって世界を往復し続けた。

**対策**: 近道を入れるときは**何を前提にしているかコメントに書き**、その前提が動く改造で真っ先に疑う。

### 4.5 データの持ち方（実際に効いた形）

- **導出できるものは保存しない**（表面高さ・連結成分・索引）。読み込み後に組み直す
- **省略可能な欄を初期化処理で埋めない**（保存→復元の一致が壊れる）
- **見た目の状態をゲーム状態に持たせない**（描画側だけで完結させると、セーブも決定論も汚れない）
- **乱数の消費数を変えない**。変えると以降の乱数列が全部ずれ、較正済みの検査が無効になる。
  種別の追加は既存の帯の再割当で行う

## 5. AI と組んで開発するときの作法

**この章が、次のプロジェクトで一番効く。**

### 5.0 ⭐ 最重要 — 「同じものを見る」を最初から設計する

**次のプロジェクトで、コードより先に作るべきものがこれ。**

#### 何が起きるか

AI は **repo（ファイル）しか見えない**。あなたは **画面しか見ていない**。
この非対称は、放っておくと必ず事故になる。

| | AI から見えるか | あなたから見えるか |
|---|---|---|
| repo のファイル・git 履歴 | ✅ | ✅ |
| 未コミットの作業ツリー | ✅ | ❌（気づかない） |
| 実行中のゲームの状態 | ❌ | ✅ |
| ブラウザ/エンジンのローカル保存（下書き・設定・セーブ） | ❌ | ✅ |
| 今そのタブ/ビルドが読んでいるコードの版 | ❌ | ❌（**誰も見ていない**） |
| 画面に実際に映っている姿 | △（粗く・一瞬だけ） | ✅ |

⚠️ **実例（このプロジェクト、2026-08-15）**: 「最初の村人の顔を2種類にして」という
1行の依頼で **4往復**した。原因は3つ同時に起きていた —
①直す箇所が3つあるのに1つしか直していない ②検査を `id 1..20` で書いたが実在するのは
`id 1..4` だけで、そこは全部同じ顔だった ③**ユーザーの「顔B」と AI の「顔B」が
別のファイルだった**（作った人の編集がローカルにあり、repo には届いていなかった）。

AI は「実装は正しい」と**3回続けて報告**した。プールの中身、500件の走査、全 id の比較 —
**どれも本当で、どれも的外れ**。ユーザーが見ているのは4人だけだった。

#### 対策 — 設計の順に

##### ① 決定論を先に確保する（これが無いと他が全部無意味）

- **乱数は種から。`Math.random()` / `Random.Range()` を禁止**し、状態が持つ PRNG に一本化
- **固定ティック**（box は 20Hz）。フレームレートで挙動が変わると比較できない
- **同じ種 → 同じ世界** を保証する。世界生成は位置の純関数 `f(seed, x, z)` にする

⭐ **「同じものを見る」は、まず「同じ入力から同じ物が出る」が前提。** ここが崩れていると、
どんな観測の仕組みを足しても「たまたま違う」を排除できない。

##### ② 実行中の状態を repo へ吐く口を、最初に作る ← **単独で一番効く**

**これ1つで非対称が消える。** ゲームが自分の状態を定期的にファイルへ書き、AI がそれを読む。

```
実行中のゲーム → POST /__live （または直接ファイル書き込み）
  → .box-live.json （git 管理外）
    → AI が読む / 照合コマンドが repo と突き合わせる
```

**中身**（box の実装。他ジャンルでも同じ骨格でよい）:

| 項目 | なぜ要るか |
|---|---|
| そのタブ/ビルドの**読み込み時刻** | サーバ起動時刻と比べて「**古いコードを動かしている**」が分かる |
| **サーバ/ビルドの起動時刻・版** | 上と対で意味を持つ |
| **アセットの件数と指紋** | 「AI の見ている素材」と一致しているか |
| **ローカル保存に残っている上書きの件数** | 0 でなければ repo と食い違っている |
| **編集中の下書きが repo と違うか** | ⭐ **今回いちばん効いた**。「作った人にしか見えていない姿」の検出 |
| **今の場面の要約**（種・経過・主要エンティティの id） | ⭐ **AI が測るべき個体そのもの**。今回の `id 1..4` |

⚠️ **重要な制約が2つ**:

1. **アセットそのものを書かない。指紋と要約だけ。** 実行中のアプリが repo の
   成果物ファイルを自動で書くと、**人の作品を壊す**（このプロジェクトで2回壊した）
2. **画面ごとに分けて持つ。** 1つの欄に上書きすると、後から申告したほうが勝って
   **もう片方が見えなくなる**（ゲームとエディタは同時に開いているのが普通）

##### ③ 照合コマンドを1つ持ち、「見た目の話の前に必ず打つ」

`npm run same` のようなコマンド1つ。**食い違っている行だけ**出す。

```
── editor http://127.0.0.1:4091/
✓ タブは今の dev server で読み込まれている
✓ 意匠 43件（画面と同数）
✗ 下書き「face_b」が repo と違う — まだゲームに出ていない
✗ repo に未コミットの変更 10件 — AI だけが見ている状態がある

── game http://127.0.0.1:4090/
✓ 村: 種 20260722 / 1日目 / 村人 4人（id 1,2,3,4）
```

⭐ **規律**: 揃っていないなら、**どちらの観察も正しく、話は永遠に噛み合わない。**
だから見た目の議論より先に打つ。今回の4往復は、この6行が全部潰す。

##### ④ 「まだ反映されていない」を画面に出す

作った物がゲームに出るまでに **手動の段**（保存ボタン・ビルド・インポート）があるなら、
**渡っていないことを常時表示する**。

- ⚠️ **文言は「未保存」ではなく「まだゲームに出ていない」**。何が困るかが伝わる語で書く
- 押したら消える。**往復を検査する**（片方向だけ確かめると、戻る側が壊れていても気づけない）

##### ⑤ 共有物すべてに短い指紋を付け、画面に出す

- 6桁の16進など、**人が読み上げられる長さ**
- アセット・ビルド・セーブそれぞれに
- ⭐ **名前で話すと食い違う。指紋で話すと1行で決着する。**
  今回、膠着を破ったのは「顔Bは**白塗りの顔に黄色の髪**」という**実物の描写**だった

##### ⑥ 状態を持つものは全部「書き出す / 読み込む」を持つ

セーブ・エディタの上書き・設定。**1つのファイルにまとめて渡せる**ようにする
（片方だけでは再現しない）。「同じ村を見て話す」が1操作でできること。

##### ⑦ AI が「1つずつ実寸で見る」道具を、アセットを作る前に用意する

⚠️ **AI が読む画像は縮小される**（このプロジェクトでは ~256px）。全体スクショでは
破綻が見えない。**要素ごとに切り出して撮れる並び画面**を先に作っておく
（box は `gallery.html` で各点に `#t-<id>` の枠を付けた）。

⭐ **順序が大事** — 意匠を作り始めてからでは、作った物を検分できない期間が生まれる。

#### エンジン別の注意

**Unity の場合**（このプロジェクトは Web だが、次が Unity なら）:

- ⚠️ **`Library/` と `PlayerPrefs` は git に入らない** = AI から見えない。
  アセットの見え方が違う原因がそこにあると、**永久に特定できない**
- **`Application.persistentDataPath` は repo の外**。観測用の状態は
  **エディタ実行時だけプロジェクト配下へ書く**（`Application.dataPath/../.live.json` など）
- **シーン・Prefab は YAML**。AI は読めるが差分が追いにくい。
  **見た目を決める値は ScriptableObject か JSON に出す**と、AI が読める・比べられる
- **UnityMCP のようにエディタ状態を直接読める道具があるなら併用する。**
  ただしそれは「エディタが何を持っているか」であって「**実行中のゲームがどう見えているか**」
  ではない。テレメトリは別途要る

#### まとめ — 一文で

> **AI が「実機で確認した」と言うとき、それは *AI の* 実機。
> どの実機かを書けない報告は、何も確認していないのと同じ。**

だから **「どの実機か」を機械が言えるようにする**のが、この節の全部。

### 5.1 溜まった報告を片付けるときは、直す前に履歴を引く

⚠️ **同じ失敗を同じ日に2件やった。** どちらも**既に直っていたものを掘り返し**、
片方は**直っていたものを壊した**。

⭐ **気づけない理由**: 観察メモに ✅ が無かった。しかし決着は別の待ち行列へ移っており、
**メモに印が無いことは「未対応」を意味しなかった**。

**対策**:
- **入口（気づきのメモ）と決着（課題の台帳）を一方通行で繋ぎ、直す前に両方を引く**
- `git log -- <そのファイル>` を1回打つ。**メモの記載日より後に修正が入っていることがある**
- 「調べたら既に直っていた」ときは、**その場で印と根拠を書く**。書かないと何度でも調べ直す
  （実際、33件中8件が既に片付いていた）

### 5.2 レビューは必ず別の目を立てる

**自分で書いた直後は「動くはず」バイアスがある。**

⚠️ 実測: 自己レビューで6件、エージェントのレビューで15件のバグが出た。
最後の全体監査では**12件の指摘のうち11件が本物**で、そのうち**2件は Critical**だった。

**効いたやり方**:
- **1体あたり2ファイルまで**に絞る（広げると溢れて成果ゼロになる）
- ⭐ **仮説を名指しで渡し、「真偽をコードで確かめて明記して」と書く。**
  「バグを探して」より遥かに精度が上がる（前回は6件中3件が誤報だった）
- **既に直っている件を明示**して重複報告を防ぐ
- ⚠️ **指摘は鵜呑みにせず自分で確かめてから直す**

### 5.3 記録の構造

- **同じ役目の入口を2つ作らない。** 作るなら一方通行の順路を同時に決める
  （気づき → 課題 → 履歴）
- **追記専用のログは、いつか grep できなくなる。** 切り出す閾値を先に決める
  （実例: 517KB / 4,216行に育ち、要約表の1行が 8,972文字になった）
- **完了した計画書を安易に移動しない。** 動かす前に「誰が名指ししているか」を数える
  （実例: コード30箇所が正典として参照していた）
- **ツールの状態は、書いてある記述ではなくツールに訊く。**
  ⚠️ 実例: 環境情報の「Git 管理下ではない」を鵜呑みにし、**4日ぶん196ファイルが未コミット**で
  放置されていた。`git log` を1回打てば済んだ

### 5.4 罠の一覧を育てる

**この開発で最も価値があった成果物は、コードではなく「罠と教訓」の一覧（最終的に76項目）。**

- 新しく踏んだら**1行足す**
- 各項目に「⚠️ 何が起きたか（具体的な数字）」と「⭐ なぜ気づけなかったか」を書く
- ⭐ **既存の項目を形の上で守っていたのに壊れた**ときは、その項目を**上書き・拡張する**
  （例:「対で入れる」→「入れたものが実際に走るか確かめる」）

## 6. 環境・道具まわり（Windows / Web）

- **「反映されない」はまず開発サーバの起動時刻を疑う。** 3日前のプロセスが生きていて、
  古い世界を見ていたことが**この開発で3回**あった。⚠️ 実測してから測定を始める
- **`.bat` に日本語を書くとその bat は黙って動かなくなる**（コンソールのコードページで読むため）。
  エラーも出ず、ただ何も起きない
- **エディタのオートセーブが repo のファイルを書いていることがある。**
  ⚠️ 実例: 「保存を押さなければ安全」と思って触ったら、**316行の差分**が出た。
  **repo を書くのは「押した人の意図がある操作」だけにする**
- **作業の後に `git status` で確かめる。**「触っていないはず」は根拠にならない —
  触ったのは自分ではなく道具かもしれない
- **検証している世界が、ユーザーの世界と同じとは限らない。**
  ブラウザのローカル保存はプロファイルごとに別物で、「私の見ている村」と
  「ユーザーの見ている村」は寸法から違っていた。**共有できる置き場（repo の中）へ寄せる**
- **計測系を自分で組む前に、既にある表示を読む。**
  ⚠️ 実例: 自前の計測が 1Hz を返して「重い」と報告しかけたが、画面には 61fps と出ていた
  （絞られていたのは計測ループの側だった）

## 7. ゲーム設計そのものについて

### 7.1 前提が変わったら、それに紐づく規則を明示的に撤回する

⚠️ 実例: 正典に「**本プロジェクトは経営ゲームである。**夜が暗くて誰がどこにいるか
分からないのは不具合」と書かれ、暗くすること自体が禁止されていた。
**その前提（俯瞰の経営ゲーム）は方針転換で消えていたのに、規則だけが残っていた。**

⭐ **教訓**: 大きな方針転換のとき、**消えた前提に紐づく規則を洗い出す**。
規則は前提より長生きする。

### 7.2 決めたことは「理由」ごと書く

「〇〇はしない」だけだと、次に同じ実測へ行き当たったとき**また調べ直す**。
実例として、調査の結論に「**この行は調べ直さないための蓋**」と書いてある項目があり、
これは実際に機能した。

### 7.3 「現状維持」も結論

比較検討して何もしないと決めたなら、**そう決めた理由を1行残す**。
残さないと同じ検討を何度も繰り返す。

### 7.4 収益や勝敗が絡む設計は、技術より先に前提を検証する

（この開発の範囲外だが、同じ轍として記録）
**「なぜ自分が有利なのか」を1文で言えないうちは、技術を作らない。**
言えないなら「収益システムではなく技術実験」と明言してから作る。

## 8. 技術的な知見（ボクセル・リグ・描画）

次にボクセル系を作るなら、ここは調べ直さなくてよい。

### 8.1 キャラの骨と動き

- **箱の階層 + 剛体回転だけで足りる。**メッシュ変形（スキニング）はボクセルの見た目を損なう
- **骨格・体型・動きは全部データにできる。**参考にした市販タイトルの形式が実際にそうなっている:
  `アニメーション → 骨 → チャンネル(回転/位置/拡大) → 打点`
- ⭐ **適用の順が肝**: **毎フレーム静止姿勢へ戻す → 組み込みの動きが値を置く → 足した動きが加算**。
  ⚠️ 戻す処理が無いと、どの枝も触らない骨で**加算が無限に積み上がる**（実測: 首が 22.58 rad = 64周ぶん）。
  この不具合は**テストでは出ない**（毎回組み直すので1フレームしか回らない）。同じリグを
  600フレーム回す検査が要る
- **骨格に無い骨は黙って飛ばす**設計にすると、体型を変えても壊れない
- **骨の「長さ」は新しい欄ではなく子の位置そのもの。**別に持つと2箇所で決めることになる
- ⚠️ **骨を伸ばしても肉は伸びない**（剛体なので当然）。隙間は彫って埋める前提で設計する
- **関節を減らすと装備が作りやすくなる。**節が増えるほど「どちらに付けるか」が掛け算で効く

### 8.2 セーブ

- **ブラウザのローカル保存には実質 5MB の壁がある。**⚠️ 実測: 1スロット 1.08MB で
  **残り0スロット**になっていた。索引付きデータベース + 圧縮へ移して 0.38MB / 10GB 枠に
- **圧縮は標準機能で足りる**（外部ライブラリ不要）
- **保存でフレームが飛ぶ**なら、まず何にかかっているか測る（実測 49.3ms → 9.1ms）
- **バイナリの塊は文字列化の経路から外す**（JSON 化で桁違いに膨らむ）

### 8.3 描画

- **「重い」は平均 fps で測らない。**1フレームの山は平均に出ない。分布と**周期**を見る
  （5秒周期 → 定期処理、と当たりがつく）
- **描画コールの数が壁になる。**影を落とす対象を距離で切ると効く
- **同じ処理を2箇所（チャンク生成と手持ち表示）で書かない** — 片方だけ質感が付かない、が起きる
- **可変フレームの物理は刻む。**1フレームの上限で1マスを超えないか必ず確かめる
- **落下の着地点を「セルの天面」に決め打ちしない。**半分の高さの床では
  押し上げ→落下→再衝突を毎フレーム繰り返す。⚠️ しかも**速く落ちた時だけ**出る形の再発もある

### 8.4 UI

- **状態依存の見た目はクラス切替に寄せる**（インラインの指定は CSS に勝ってしまう）
- **毎フレーム DOM を作り直すとクリックが成立しない**（押してから離すまでに要素が消える）
- **3D の上に浮く窓は自前の地の面を必ず持つ**
- ⚠️ **CSS のコメントを1行消すと、その下の規則が丸ごと消えることがある**
  （開きしるしごと消えて閉じしるしだけ残る）。型もテストも通り、**5日間誰も気づかなかった**

## 9. 次のプロジェクトで最初にやること

**着手前に、この順で。**

0. ⭐ **「AI と同じものを見る」仕組みを、コードより先に置く**（§5.0）。順に:
   **①決定論**（種・固定ティック・`Math.random()` 禁止）→ **②実行中の状態を repo へ吐く口**
   （タブの版・アセットの指紋・下書きが repo と違うか・**今の場面の主要 id**。⚠️ **指紋と要約だけ。
   アセット本体は書かない**）→ **③照合コマンド1つ**（見た目の話の前に必ず打つ）→
   **④「まだゲームに出ていない」の常時表示** → **⑤1つずつ実寸で撮れる並び画面**（意匠を作る**前**に）。
   ⚠️ **これを飛ばすと、AI は自信を持って別の世界の報告をしてくる**（実例: 1行の依頼で4往復）
1. **記録の入口を1つだけ決める。** 気づきをどこに書くか、決着をどこへ移すか、一方通行で
2. **「罠と教訓」のファイルを最初に作る。** 空でよい。踏んだら1行足す
3. **単位を決めて、距離は必ず `値 × 単位` の形で書くと決める。** 上限・回数には掛けない
4. **「唯一の出所」を決める習慣を最初から。** 値・分類・判断のどれも
5. **保存の形式を先に決める**（容量の壁は後から必ず来る）
6. **検査は「ファイル数が合っているか」で見ると決める。** 件数は嘘をつく
7. **見た目を触る作業の手順を決める**: 目標を数字で決める → 作る → **切り出して撮る** →
   機械で判定 → **自分の目で見る** → 直す。⚠️ **ユーザーに検証させたら、その時点で手順は破れている**
8. **レビューは別の目を立てると決める。** 自己レビューだけで本番に出さない

## 10. 最後に — この開発で一番効いた考え方

**「動くはず」と思った瞬間が、一番危ない。**

この記録にある失敗のほとんどは、技術的に難しかったから起きたのではない。
**確かめられたのに確かめなかったから**起きている。

- `git log` を1回打てば分かった
- 対照を1回取れば分かった
- スクショを1枚見れば分かった
- 定義ファイルを1行引けば分かった

⭐ そして**確かめる仕組みを持てば、確かめる意志は要らなくなる。**
検査・空振り検査・見た目の輪・別の目のレビューは、どれも「意志に頼らない仕組み」だった。
次のプロジェクトでは、**この仕組みを最初の日に置く**。

そしてもう一段深いところに、**確かめる対象そのものがずれている**という失敗がある。
AI は repo を、人は画面を見ていて、**どちらも自分の世界では正しい**。
これは意志でも注意力でも埋まらない — **見ているものを機械が突き合わせる**しかない（§5.0）。

> **「実機で確認した」は、どの実機かを書かなければ、何も確認していないのと同じ。**
