# ゲーム制作の定義と手法

**「よく分からないまま着手し、作りながら分かってきたこと」を、次に最初から使える形にまとめたもの。**
対象: ボクセル村シミュレーション「境木の村」(box)。2026-07 〜 2026-08。

前作の報告書『ゲーム開発から学んだこと』が**エンジニアリングの失敗と検証の作法**を扱うのに対し、
こちらは**ゲームを作るという行為そのもの**について。

⚠️ **この文書の一番大事な前提**: このプロジェクトは途中で**ジャンルごと作り替えた**。
タワーディフェンス + 経営シムとして始まり、1か月後に **Minecraft × RPG × Breeding** になった。
だから以下は「最初から分かっていた人の整理」ではなく、**間違えた側からの記録**である。

---

## 1. 一番大きな発見 — 「作りたいゲーム」は作らないと分からない

### 1.1 何が起きたか

最初はタワーディフェンスだった。塔・バリスタ・射線・防衛の較正・弓兵・城壁。
かなり作り込んだ後、遊んでみて**面白くないことが分かった**。

転換の日にやったのは、**引き算だけ**だった:

| 消したもの |
|---|
| 塔の火力 / 撃つ設備5種 / 弓兵 / 罠 / 鐘楼 |
| 建物の耐久（壊れる仕組み） |
| 領地・村の礎・開拓・町の自動設計 |
| 隊商・討伐・派遣・斥候・遺物・魔法陣 |
| 旧ボスとその前振り |
| ゲームオーバー |

そして残ったものに、**血統・繁殖・パーティ・冒険**を載せた。

### 1.2 何を学んだか

⭐ **企画書の段階で「面白いか」は分からない。作って遊ぶまで分からない。**
だから重要なのは**正しく企画すること**ではなく、**間違いに早く気づいて捨てられること**。

**捨てやすくする作り方**:
- **各段階は必ず動く状態で終える。**「全部揃ったら動く」作りにしない
- **将来を見越した足場を先に組まない。**捨てるとき足場ごと捨てることになる
- **系統ごとにファイルを分ける。**塔を消すとき、塔のファイルを消すだけで済む状態にしておく

⚠️ 逆に**捨てにくくしていたもの**は、「いつか使う」と思って作った抽象と、
複数の系統にまたがって書いた条件分岐だった。

### 1.3 転換のときにやるべきこと

**消えた前提に紐づく規則を洗い出す。** 規則は前提より長生きする。

⚠️ 実例: 正典に「**本プロジェクトは経営ゲームである。**夜が暗くて誰がどこにいるか
分からないのは不具合」と書かれ、画面を暗くすること自体が**禁止**されていた。
経営ゲームという前提は転換で消えていたのに、**禁止だけが1か月残り**、
「夜を暗くしたい」と言われた日に初めて掘り起こされた。

## 2. ゲームの定義 — このプロジェクトで固まった言い方

作りながら、いくつかの言葉に**自分たちなりの定義**ができた。次でもそのまま使える。

### 2.1 ゲーム = ループ

企画を1枚で言うとき、**箇条書きの機能表ではなくループを書く**と決めた。

```
探索・採取・採掘・戦闘 → 資源と経験値 → 村を発展 → 村人を育てる → 繁殖する
  → 遺伝と突然変異で新しい個体 → 厳選 → 装備を整える → パーティ編成
  → ダンジョン・ボスへ挑む → 最初へ戻る
```

⭐ **ループで書くと「機能が足りているか」ではなく「輪が閉じているか」で判断できる。**
機能表だと足し算しか起きないが、ループだと「ここが繋がっていない」が見える。

### 2.2 体験の核 = 判断に迷ったとき戻る一文

```
自分で育てた血統を使って冒険する。
```

そして**判断に迷ったら「これはプレイヤーが〇〇する方向に働くか」を問う**と決めた。

⭐ これは**思想の飾りではなく、実務の道具**。「この機能を入れるか」で議論が割れたとき、
好みではなく核との距離で決められる。

### 2.3 「村」と「勝敗」を切り分ける

```
村は冒険と育成を支える拠点。村人はクリアするための手段。
村は勝敗を決めない。育たなければ弱いだけ。
```

⭐ **何が勝敗を決めるかを1つに絞る**と、それ以外を安心して緩められる。
村づくりが勝敗を決めるなら村づくりに厳密なバランスが要るが、決めないなら要らない。

### 2.4 報告の3分類 — バグ / 仕様の空白 / 調整

遊んで気づいたことを片付けるとき、**この3つに機械的に振り分ける**と決めた。

| 種類 | 見分け方 | やること |
|---|---|---|
| **バグ** | 期待が正典どおり | 直す |
| **仕様の空白** | 期待が正典に無い | **決める**（作者に訊く） |
| **調整** | 動いてはいるが数字が悪い | 遊んで決める |

⭐ **効いたのは「期待」を必ず書かせたこと。**
「〇〇がおかしい」だけだと分類できないが、「**どうなると思ったか**」があると一発で分かる。

### 2.5 「未決」を明示する

決まっていないことに **🚧 未決** の印を付け、**推測で実装しない**と決めた。

⚠️ これが無いと、実装者（人でも AI でも）が善意で埋めてしまい、
**作者が決めたつもりのないものが仕様になる**。しかも既成事実になると覆しにくい。

## 3. 引き算の手法

**足すより難しく、効果が大きい。**

### 3.1 「数を増やさない」を先に決める

- **食べものは4種**で「拾う → 焼く/干す → 蓄える」の段が作れる
- **彫刻ブロックは本家にあるものだけ**（階段・ハーフ・薄板・格子）。斜めは1つも無い
- **戦闘職は1つ**に統合し、違いは**持つ武器**で出す

⭐ **種類を増やすと、掛け算で検証が増える。**
「4種で足りるか」を先に問うほうが、後から減らすより遥かに安い。

### 3.2 「効率の選択」を作らない

**建材の違いは色だけ**と決めた。形も素材も、性能差を付けない。

⭐ **理由**: 性能差を付けると「どれを使うのが得か」の計算がゲームの中心になる。
見た目の選択でいてほしいものを、最適化問題にしない。

### 3.3 プレイヤーの仕事を奪わない

⚠️ 実例: 「夜に村人が誰も屋内へ逃げない」を調べたら、原因は AI ではなく
**初期村に寝床が1つも無い**ことだった。救済（初期村に寝床を置く／自動で退避先を作る）を
入れかけて、やめた。

> **逃げ込む先はプレイヤーが作るものなので何もしない。**

⭐ **家を建てるのがプレイヤーの仕事なら、建てなければ夜が危ないのは正しい因果。**
親切に見える救済は、**やることを1つ奪う**。

### 3.4 消した機能の跡地を残さない

⚠️ 実例: 討伐システムを消したとき、会話画面のボタンと受け側の関数群が**丸ごと残り**、
2か月後に「戦士の窓に意味不明なボタンがある」と報告された。

**対策**: 消すときは**入口・受け側・データ・表示**を同時に消す。1つでも残ると幽霊になる。

## 4. 「面白さ」をどこから出すか

作りながら、**面白さの出どころ**が具体的に見えてきた。

### 4.1 愛着は「取り返しがつかない」から生まれる

**死んだ村人は完全ロスト。寿命は無い。**

⭐ 寿命が無いので世代交代は自動では起きない。繁殖は「**もっと良い個体が欲しい**」という
動機だけで回る。そして死が取り返しつかないので、**連れ出す判断に重みが出る**。

### 4.2 トレードオフが判断を作る

**村人を連れ出すと村の仕事が止まる。**

⭐ これは「不便」ではなく**設計の軸**。
強い個体をパーティに入れるほど村が回らなくなるので、毎回選ばされる。

### 4.3 「見えない」ことが理由を作る

夜を暗くしたとき、守る線を2つに決めた。

```
自分の周りは読める / 遠くは分からなくてよい
```

⭐ **遠くが見えないから、夜に出るのが怖い。**
全部見えている世界に「向こう側に何かある」は生まれない。**山も隠すためにある。**

### 4.4 世界は「手で置く」ほうがわくわくする

最初は完全な自動生成だった。作者の指摘は
**「サンドボックスとしては十分だが、RPG のマップとして見るとわくわくしない」**。

**世界を1つに固定**し、地区・危険度・目印・山脈を**手で置いた表**にした。
シードが変えるのは**村と血統だけ**（＝プレイヤーが作ったもの）。

⭐ **自動生成は「毎回違う」を作るが、「ここに何かある」は作れない。**
どちらが要るかは、ジャンルで決まる。

## 5. バランスと数値の決め方

### 5.1 実測してから決める（勘で置かない）

⚠️ 実例: 「木の採取量が少なすぎて家が建たない」という報告に対し、感覚で上げずに測った。

```
手で積む最小の家 = 48ブロック = 木材194
村の 40m 以内の木 = 29本 → 旧設定では 0軒
```

**そのうえで**「最低1軒は建つ」を最低線に置いて数値を決めた。

⭐ **数値の議論は「何を保証したいか」を決めれば終わる。**
決めないと好みの言い合いになる。

### 5.2 比を変えるときは「何と何の比か」を先に決める

⚠️ 実例: 一撃死を無くそうとして HP と攻撃力を**同じ倍率**で上げたら、
比が変わらないので**一撃死は消えなかった**。倍率を分けて初めて手数が増えた。

### 5.3 「爆益」より「破綻しないこと」を先に見る

評価の優先順を固定した:

```
1. 破綻の回避  →  2. 安定性  →  3. 頑健さ  →  最後に  期待値
```

⭐ **1回の大勝ちに依存する設計を、良い設計と誤認しない。**

### 5.4 較正した数値は、根拠ごと残す

数値の横に**どう測ったか**を書く。書かないと、次に触る人が測り直すか、勘で動かす。

⚠️ 逆に**根拠を書かずに置いた数値**は、後から「なぜこれなのか」が誰にも分からなくなり、
動かせない・直せない塊になった。

## 6. 見た目の作り方（制作の観点から）

### 6.1 「正解」を先に決める

```
見た目の正解は Minecraft と ARK。
```

⭐ **これを決めた効果が大きかった。**
「良いか悪いか」は好みで割れるが、「**本家とどう違うか**」なら測れる。
迷ったら本家の定義ファイルを引けば答えが出る。

### 6.2 意匠は「コードに書き下ろして終わり」にしない

**ボクセルで作るものは必ずエディタを経由する**と決めた。
コードに置くのは**叩き台**まで、仕上げはエディタ（＝人の目と手）。

⭐ **理由は2つ**: ①目で見て直せるのは人だけ ②コードに書いた座標は後から誰も直せない。

そして**新しい種類の資産を足すときは、先にエディタで編集できるようにしてから中身を作る。**

### 6.3 質を保つのは「意志」ではなく「輪」

「できました」と言ってから見ると品質が悪い、が何度も起きた。原因は道具ではなく
**止まる仕組みが無かった**こと。手順を固定した:

```
目標を数字で決める → 作る → 切り出して撮る → 機械で判定 → 自分の目で見る → 直す
```

⚠️ **完了の条件は2つとも**: 機械の検査が通る **かつ** 自分で画像を見て目標を満たしている。
**作者に検証させたら、その時点でこの手順は破れている。**

## 7. 作り方の運び方

### 7.1 段に切る。各段は必ず動く状態で終える

大きな転換も、**段1（撤去）→ 段A（器）→ 段B（画面）→ 段C（仕組み）…** と切った。
それぞれの段の終わりで遊べる。

⭐ **効いたのは「撤去」を最初の段に置いたこと。**
足しながら消すと、どちらの都合で壊れたか分からなくなる。

### 7.2 記録は一方通行にする

```
気づき (遊んで書く) → 課題 (分類して決める) → 履歴 (やったことを残す)
```

⚠️ 同じ役目の入口を複数作ると、**どこに書くか誰も決められず放置される**。
実際、気づきの置き場が4つあり、どれも単体では正しかったが次の指摘をどこに書くか決められなかった。

### 7.3 決めたことは理由ごと書く。「調べ直さないための蓋」を置く

⭐ 調査の結論に「**この行は調べ直さないための蓋**」と明記した項目があり、実際に機能した。
「〇〇はしない」だけだと、次に同じ実測へ行き当たったときまた調べ直す。

### 7.4 「現状維持」も結論

比較検討して何もしないと決めたなら、**そう決めた理由を1行残す。**
残さないと同じ検討を何度も繰り返す。

### 7.5 遊ぶ時間を工程に入れる

⚠️ この開発で見つかった問題の**最も価値ある一群は、作者が遊んで書いたメモ**から出た。
検査でもレビューでも出てこない種類（手触り・分かりにくさ・違和感）がそこにしか無い。

**遊ぶ → メモ → 分類 → 直す**を回すのが、実質的な品質保証だった。

## 8. 個人開発 × AI という体制について

このプロジェクトは**作者が方向を決め、AI が実装する**形で進んだ。そこで分かったこと。

### 8.1 AI に決めさせてはいけないもの / 任せてよいもの

| 任せてよい | 作者が決める |
|---|---|
| 実装・リファクタ・検査 | **面白いかどうか** |
| 調査・比較・棚卸し | ジャンル・体験の核 |
| 数値の**測定** | 数値の**目標** |
| 見た目の叩き台 | 見た目の**採否** |

⭐ **境界は「取り消せるか」で引ける。**
コードは書き直せるが、**方向を間違えた1か月は戻らない**。

### 8.2 指示の解像度が成果を決める

効いた言い方:
- 「**期待**」を必ず書く（どうなると思ったか）
- 「**この仮説の真偽をコードで確かめて明記して**」（「探して」より精度が上がる）
- 「**通貫で**」（確認ゲートを置かない、と最初に宣言する）
- 「**現状維持も結論**」（何もしない選択を許可する）

### 8.3 AI は「既に直っている」を掘り返す

⚠️ この開発の最終盤、**同じ日に2件**、既に決着していたものを掘り返した。
片方は**直っていたものを壊した**。

**対策**: 記録を一方通行にし（§7.2）、**直す前に履歴を引く**ことを規則にする。
そして「調べたら既に直っていた」ときは**その場で印と根拠を残す**。

### 8.4 レビューは必ず別の目を立てる

自分で書いた直後は「動くはず」バイアスがある。実測で、
**自己レビュー6件に対しエージェントのレビューで15件**のバグが出た。

## 9. 次のゲームを始めるときの手順

**この順でやる。**

1. **ループを1枚書く。**機能表ではなく輪で。輪が閉じているかだけ見る
2. **体験の核を一文で書く。**迷ったとき戻る場所として
3. **何が勝敗を決めるかを1つに絞る。**それ以外は緩めてよいと決まる
4. **見た目の「正解」を決める**（参考にする実在のタイトル）。好みの議論を測定に変える
5. **やらないことを先に書く。**禁止リストは、後から書くと手遅れになる
6. **記録の入口を1つ決める**（気づき → 課題 → 履歴の一方通行）
7. **最小のループが動く所まで最短で行く。**そこで**遊ぶ**
8. **遊んで違うと思ったら、足すのではなく引く。**引けるように作っておく

---

## 10. 最後に

⭐ **この1か月で一番価値があった行為は、実装ではなく「捨てる決断」だった。**

タワーディフェンスを作り込んだ時間は無駄ではない。**それを作らなければ、
「作りたいのはこれではない」と分からなかった**からだ。

ただし次は、**もっと早くその地点に着ける**はずである。
最小のループを最短で動かし、遊び、違えば引く。それだけで、
今回1か月かかった判断は、おそらく1週間で出せる。

**企画は当てるものではなく、外れを早く見つけるもの。**
